# ADR-0002. Связь с автомобилями — отдельный контейнер «Телематический шлюз»

**Дата:** 2026-10-26
**Статус:** принято
**Область:** архитектура (`docs/06-c4/02-container.puml`, `05-deployment.puml`)

## Контекст

Открытие по телефону (ВИ-04) и завершение аренды (ВИ-05) требуют связи с
бортовым модулем каждого автомобиля. Ограничения:

- у автомобиля в мобильной сети LTE нет входящего адреса, поэтому соединение
  должен открывать сам модуль и держать его постоянно;
- соединений столько же, сколько автомобилей в парке (тысячи), а запросов от
  клиентов к API на порядки меньше, и характер нагрузки разный;
- требование надёжности из `traceability.md`: до 3 повторов команды, итог
  не дольше 10 секунд.

## Рассмотренные варианты

1. **Модуль внутри Backend API.** MQTT-клиент и логика повторов — компонент
   Spring-приложения. Плюсы: на один контейнер меньше, нет сетевого вызова
   gRPC. Минусы: каждый из 3 экземпляров API держал бы долгоживущие
   соединения с автомобилями; при выкладке новой версии API все автомобили
   переподключаются разом; соединения и REST-нагрузка масштабируются вместе,
   хотя растут по разным причинам.
2. **Отдельный контейнер «Телематический шлюз» (Go).** Держит соединения
   MQTT/TLS, переводит их в gRPC для API. Плюсы: выкладка API не рвёт связь
   с парком; шлюз масштабируется по числу автомобилей, API — по числу
   клиентов; протокол конкретного производителя модулей изолирован в одном
   месте. Минусы: ещё один контейнер в сборке и мониторинге; лишний сетевой
   переход внутри кластера.
3. **Облачная IoT-платформа (например, Yandex IoT Core / AWS IoT Core).**
   Плюсы: соединения, сертификаты устройств и масштабирование — забота
   провайдера. Минусы: привязка к провайдеру и его ценам за сообщение; у
   части производителей бортовых модулей свой протокол поверх TCP, а не MQTT,
   и его всё равно пришлось бы адаптировать своим сервисом.

## Решение

Вариант 2. Решающий довод — независимость выкладки: Backend API меняется
часто, а разрыв связи с парком во время выкладки означает, что клиенты не
могут открыть автомобили. Вариант 3 отвергнут из-за разнородности протоколов
модулей: адаптер всё равно нужен, а платформа добавила бы к нему зависимость
от провайдера.

## Последствия

**Плюсы:** выкладка API не затрагивает автомобили; `TelematicsClient` в API —
единственное место, где живут повторы и таймауты команд.
**Минусы:** два экземпляра шлюза должны знать, кто из них держит соединение с
конкретным автомобилем (маршрутизация команд), — отдельная задача, не
смоделированная здесь (см. `ARCHITECTURE.md`, раздел 8).
**Что станет неверным, если решение пересмотреть:** C4 Container, Component
(`TelematicsClient`), Dynamic (шаги 3–4, 9), диаграмма развёртывания.
